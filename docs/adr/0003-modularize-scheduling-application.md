# ADR-0003：调度主应用采用 Maven 模块化单体

- 状态：已采纳
- 日期：2026-08-19

## 背景

现有工程最初按独立 Action 编排服务创建，但产品边界已明确：Action 管理只是坤灵调度主应用的一个业务模块，后续还会接入两个业务模块。如果继续使用单一源码集，启动配置、业务代码、数据库迁移和页面资源会逐渐混杂，团队职责也难以通过构建依赖约束。

## 决策

采用一个部署进程、多个 Maven 模块的模块化单体：

1. 根工程命名为 `kunling-scheduling`，只负责聚合模块和统一技术基线；
2. `scheduling-app` 是唯一可执行模块，只负责启动、部署配置和模块装配；
3. `scheduling-action` 独立拥有 Action 的领域、应用、适配器、数据库迁移、页面和测试；
4. Action 模块仅通过 `ActionModuleConfiguration` 接入主应用，主应用不得依赖模块内部实现类；
5. `application.yml` 只维护部署技术项，Action 业务默认值由模块内部只读配置对象和常量集中管理；
6. 后续业务模块以同级 Maven 模块接入，每个模块提供一个明确的配置入口；
7. 业务模块默认不得相互添加 Maven 依赖。出现真实跨模块协作时，先定义小而稳定的模块接口，再由调用方依赖接口或由主应用完成编排；
8. 所有模块共用一个 MySQL/Flyway 实例时，迁移版本必须在整个部署单元内唯一。现有 Action `V1`–`V4` 保持不可变，后续模块接入时统一登记版本区间。
9. 一期机器人长连接只服务 Action 调用，放在 `scheduling-action` 的 `robotbridge` 内部包；它通过小型传输接口与动作状态机隔离，不再建立独立 Maven 模块。未来出现第二个真实使用方时，再评估抽取稳定接口模块。

## 模块接入规则

新增业务模块至少包含：

```text
scheduling-<module>/
├─ pom.xml
└─ src/main/java/com/kunling/scheduling/<module>/
   └─ <Module>ModuleConfiguration.java
```

主应用只允许增加两类改动：

1. 在 `scheduling-app/pom.xml` 增加模块依赖；
2. 在主应用启动类中显式导入模块配置入口。

如果接入一个模块还需要修改 Action 的领域、控制器或适配器，说明 seam 放置错误，应先调整模块接口。

## 结果

- 一个可部署包，避免当前阶段引入微服务通信和运维复杂度；
- Maven 编译依赖保证 Action 模块不能反向依赖主应用；
- 每个团队可以独立维护自己的源码、资源、迁移和测试；
- 后续模块可增量接入，不需要继续扩大 Action 包或启动类职责；
- HTTP 路径和现有 Action 数据表保持兼容。

## 放弃的方案

- 继续使用单 Maven 模块并仅按 package 分类：约束较弱，部署配置和依赖容易再次混入业务包；
- 立即拆为多个微服务：当前模块仍共享部署和事务基础，拆分会过早引入网络、鉴权、可观测性和分布式一致性成本；
- 创建通用 `shared` 模块承载所有公共代码：在出现两个真实复用方前会形成不稳定的公共依赖中心。
