# ADR-0002：上游原子契约采用当前目录与唯一消费 ID

- 状态：已被 ADR-0004 取代
- 日期：2026-08-18

## 背景

上游原子能力由硬编码 Adapter 提供，并只维护当前实现，不需要同时运行同一能力的多个不兼容版本。上游调用链已经具备唯一消费 ID，因此继续要求原子能力版本、机器人可用性预检查和独立幂等请求头会扩大接口，却不能增加实际安全性。

## 决策

1. 上游能力目录只以稳定 `capabilityKey` 标识当前能力，不提供原子能力版本。
2. 下游同步目录后，根据 Schema、资源、副作用和安全属性计算 `contractHash`。
3. Action 发布计划固定 `contractHash`；当前能力契约变化后，旧计划禁止启动并要求重新编译发布。
4. 删除机器人可用性前置检查。原子动作提交结果是能否受理的唯一依据。
5. 每个原子节点使用稳定 `consumeId = actionInstanceId + ":" + nodeOrdinal`。
6. `consumeId` 同时承担上游唯一消费、持久去重和状态查询职责，不再发送独立 `Idempotency-Key`。
7. 厂商任务号属于执行证据，不作为跨系统主标识。

## 结果

- 上游接口从四类减少为当前目录、提交和查询三类；
- Action 版本仍完全由下游管理；
- 上游无需维护没有实际执行含义的原子版本号；
- 可用性检查的时序竞争被消除；
- 唯一消费 ID 不再以请求头和请求体重复表达；
- 上游必须对 `consumeId` 建立持久唯一约束，并在重启后保留状态。

## 兼容策略

- V1 旧草稿中的 `capabilityVersion` 在读取时忽略，重新保存后自然移除；
- V1 旧发布计划没有 `contractHash`，可以读取和审计，但禁止发起新实例；
- V1 未完成执行实例在进程恢复时继续进入 `UNKNOWN_HOLD`，不会自动重放；
- 数据库 V4 将目录唯一键改为 `capabilityKey`，并把节点命令标识迁移为 `consumeId`。

## 重新评估条件

只有上游未来需要同时提供同一 `capabilityKey` 的多个不兼容实现，并允许调用方明确选择旧行为时，才重新引入由上游拥有的原子能力版本。
